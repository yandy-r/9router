# YAN-385 Cursor PKCE login, refresh, and usage: business research

## Executive Summary

Cursor is the only OAuth-category provider in 9router with no browser login, no refresh, and no usage probe. Today a connection can only be created by importing `accessToken` and `machineId` from a local Cursor IDE `state.vscdb`. The stored `expiresAt` is a hard-coded `now + 24h`, although the real JWT lives about 60 days, and the executor opts out of refresh entirely. This feature adds three things:

1. A server-polled PKCE "deep control" browser login. It works on remote or Docker deployments, where auto-import is loopback-only.
2. Real refresh through `POST api2.cursor.sh/auth/exchange_user_api_key`, with `expiresAt` taken from the JWT `exp` claim.
3. A Cursor usage handler (`GetCurrentPeriodUsage` plus `GetPlanInfo`) that feeds Provider Limits, the quota snapshot store, and the weighted account strategy (plan tier to `PLAN_CAPACITY`).

Most of the plumbing already exists. The device-code route, re-login dedup, background refresh, quota poller, and weighted selector are all in place. The work is mainly a new provider module, registry and config entries, and a handful of targeted fixes. One of those fixes is required: Cursor's error classifier currently collapses `unauthenticated` errors to 400, which means refresh and fallback never fire.

## User Stories

- **US-1 Browser login (primary).** As a dashboard user, including one running 9router in Docker or on a remote host without Cursor IDE, I click "Login with browser". Cursor's login page opens and I approve it. The connection then appears without copying anything by hand.
- **US-2 Import fallback.** As a user with Cursor IDE installed locally, I can still auto-import or paste `accessToken` and `machineId`. This is useful if the browser flow breaks upstream.
- **US-3 Re-login upgrades, never duplicates.** When I log in with the browser to a Cursor account I previously imported, the existing row gets a refresh token and correct expiry. My priority, weight, manual plan tier, proxy, and machine ID stay as they were, and no "Account 2" row is created.
- **US-4 Multiple accounts.** I can add several different Cursor accounts. Each one becomes its own row with its own machine ID, and each is rotated by the configured strategy.
- **US-5 Silent renewal.** My browser-login connections keep working past the token's lifetime without any action from me. Background refresh or on-401 refresh rotates them.
- **US-6 Honest expiry and re-auth signal.** Imported connections, which have no refresh token, show their real expiry (about 60 days). When a token is revoked or expired and refresh fails, the connection shows an error and routing skips it. I am told to log in again.
- **US-7 Usage visibility.** In Provider Limits I see, for each Cursor account, the plan name (for example "Ultra") and these rows: Total %, Auto + Composer %, API %, and On-demand $ used/limit. All rows show the billing-cycle reset time.
- **US-8 Quota-aware routing.** With the `weighted` strategy, a Cursor Ultra account gets about 20x the share of a Pro account. An account whose Cursor-reported total usage is near 100% drops to weight 0 until `billingCycleEnd`.

## Business Rules

### Core

1. **Identity key is the JWT `sub`.** Cursor session JWTs carry `sub` in the form `auth0|user_…` or `google-oauth2|user_…`, and normally have no `email` claim. The existing `CursorService.extractUserInfo` (`src/lib/oauth/services/cursor.js:132-156`) already returns `email = decoded.email || decoded.sub` and `userId = decoded.sub`. Imported rows therefore already persist `email = sub`. The browser flow must persist the same `email` value so that the dedup in `createProviderConnection` (`src/lib/db/repos/connectionsRepo.js:189-221`) matches imported rows. The match is on `authType === "oauth"` plus equal `email`, with no `username` or `chatgptAccountId` on either side. Do not replace `email` with a human-readable address fetched from another endpoint unless you also migrate existing rows or add a `userId`-based match. Otherwise the dedup breaks. If you want a readable label, put it in `displayName`.
2. **machineId is per connection and stable.**
   - When a browser login creates a new account, generate the ID on the server: `crypto.randomUUID()` passes the existing validation `^[a-f0-9-]{32,}$`.
   - On re-login to an existing row, keep the existing `providerSpecificData.machineId`. `mergeReloginProviderData` (`connectionsRepo.js:164-176`) lets fresh values override stored ones, so the new flow must either not send `machineId` on re-login or special-case it.
   - Never change `machineId` during refresh. `mergeRefreshedCredentials` only merges `providerSpecificData` when refresh returns it (`open-sse/services/oauthCredentialManager.js:105-110`).
   - The executor throws if `machineId` is missing (`open-sse/executors/cursor.js:283-291`).
3. **`authMethod` tracks provenance.** Import stays `"imported"`. Browser login should use a distinct value such as `"browser"` or `"pkce"`. Re-login switches an imported row to the new method.
4. **Expiry comes from the JWT `exp`.** Do this for import, browser login, and every refresh. Replace the hard-coded `expiresIn: 86400` in `validateImportToken` (`src/lib/oauth/services/cursor.js:120-126`) and `providers/cursor.js:11`. If the token is not a decodable JWT, fall back to a conservative default and do not throw. The pi-cursor reference falls back to 1h and subtracts a 5-minute margin.
5. **Refresh applies only when a refresh token exists.**
   - Refresh is `POST https://api2.cursor.sh/auth/exchange_user_api_key` with `Authorization: Bearer <refreshToken>` and body `{}`. It returns `{accessToken, refreshToken?}`.
   - Keep the old refresh token if none is returned. `mergeRefreshedCredentials` already does this (`oauthCredentialManager.js:90-91`).
   - Imported rows (`refreshToken: null`) are skipped by background refresh (`src/sse/services/backgroundTokenRefresh.js:55`) and by `getAccessToken` (`open-sse/services/tokenRefresh.js:183-189`).
6. **Refresh failure has two classes.**
   - _Transient_ (network error, 5xx): return `null`. The request continues with the current token (`src/app/api/usage/[connectionId]/route.js:58-63`), and the background tick retries.
   - _Permanent_ (401/403, revoked or invalid refresh token): return `{ error: "unrecoverable_refresh_error" }`, following the Codex pattern (`open-sse/services/tokenRefresh/providers.js:323-334`) and using `classifyOAuthRefreshError` (`:280-299`). Note that nothing today persists an unrecoverable result to the connection (see Gotchas). Cursor 401s on chat already lock the account for `COOLDOWN.long` via `ERROR_RULES` (`open-sse/config/errorConfig.js:81`).
7. **Usage percentages are Cursor's own values.**
   - Show `planUsage.totalPercentUsed`, `autoPercentUsed`, and `apiPercentUsed` as reported. They include bonus usage, so never derive them from `spend / limit`.
   - Clamp to [0, 100] for bars and snapshot fractions.
   - On-demand is a dollar amount (`spendLimitUsage.individualLimit`/`individualRemaining`, or `pooled*` for teams, in cents). Show it as used/limit in dollars. It is not a plan-quota window.
   - The reset for every row is `billingCycleEnd`, in epoch milliseconds.
8. **Plan name comes from `GetPlanInfo.planInfo.planName`.** Examples: "Free", "Pro", "Pro+", "Ultra", "Business". It is shown as `usage.plan` and passed through `sanitizePlanTier` (lowercases it) as the detected `planTier`. A manual `planTier` (`planTierManual: true`) always wins (`src/sse/services/accountSelection.js:37-44`, `quotaSnapshotSync.js:153-156`).
9. **Plan capacity.** Add `PLAN_CAPACITY.cursor` (`open-sse/config/quotaSnapshot.js:19-55`) with keys that match the lowercased plan names. Suggested values: `free: 0.05`, `pro: 1`, `"pro+": 3` (\_verify), `ultra: 20`, and business or team at 1 (\_verify). This table also drives the manual plan-tier dropdown and PUT validation (`src/shared/components/EditConnectionModal.js:109`, `src/app/api/providers/[id]/route.js:29`).
10. **Snapshot window mapping** in `kindForName` (`src/sse/services/quotaSnapshotSync.js:57-100`) has no `cursor` case today, so no windows would be recorded. Minimum mapping: Total goes to `"month"`, a global kind that binds every model. Auto + Composer and API are model-family scoped (see Open Questions). On-demand $ must not map to a window, because it is overflow spend, not plan quota. `planTierFor` (`:112-135`) needs a `cursor` case that returns `usage.plan`.
11. **Cursor stays a subscription provider for sticky rotation.** It is already listed in `OAUTH_SUBSCRIPTION_PROVIDERS` (`src/sse/services/accountSelection.js:5-13`, plus UI copies in `ConnectionsCard.js:24-32` and `providers/[id]/page.js:1068-1076`). The default weighted sticky window is 3, and nothing needs to change here.

### Edge cases

- **Existing imported connections.** Leave them as they are: no refresh token, `authMethod: "imported"`, 24h `expiresAt`. Because `expiresAt` is 24h in the past but no refresh token exists, `shouldRefreshCredentials` returns true on every request (`oauthCredentialManager.js:49-55`). The request path then calls `refreshTokenByProvider`, which returns `null` when there is no RT, so nothing breaks. Optional: a one-shot backfill, like `backfillCodexEmails` (`src/lib/oauth/providers/index.js:230-262`), that rewrites `expiresAt` from each imported token's `exp` so the UI stops showing them as expired.
- **Re-import after browser login.** The import route always sends `refreshToken: null` (`src/app/api/oauth/cursor/import/route.js:38`). Through the dedup merge, this overwrites a good refresh token with null, because `null` is a defined value in `{...existing, ...normalized}`. Rule: import must not clear an existing refresh token for the same `sub`. Omit the field when it is null.
- **Two different Cursor accounts in one browser.** Each poll `uuid` resolves to whichever account approved it. Different `sub` values produce distinct rows, as expected.
- **Poll abandoned or cancelled.** Nothing is persisted until a successful poll. No server state needs cleanup if polling is client-driven, as it is for qoder.
- **Token revoked upstream** (user logs out of all sessions on cursor.com). The next chat receives a Connect `unauthenticated` error. That must surface as HTTP 401 to trigger refresh, and if refresh fails permanently, the account locks and routing falls back. Today `classifyCursorError` maps every non-`resource_exhausted` structured error to 400 (`open-sse/executors/cursor.js:237-263`). A 400 is request-scoped (`accountFallback.js:66-75`): no refresh, no fallback, and the user sees a confusing error.
- **Quota exhausted.** A `resource_exhausted` error maps to 429 (`cursor.js:250-256`), which applies exponential backoff up to 4 min (`ERROR_RULES` 429). Cursor's real reset is `billingCycleEnd`, which can be weeks away, but `markAccountUnavailable` caps `resetsAtMs` at `MAX_RATE_LIMIT_COOLDOWN_MS` (30 min, `src/sse/services/auth.js:342-349`). Weighted routing covers this gap: once the snapshot shows Total at 100%, weight is 0 (below `floor: 0.05`) and the account is skipped until the window resets. Under fill-first or round-robin, the account keeps being retried after each backoff.
- **Free plan or no subscription.** `GetCurrentPeriodUsage` may return `enabled: false` or no `planUsage`. Return `{ plan, message }`, not zero-filled quotas. The poller treats a `message` as a failure and applies a 15-min cooldown (`src/shared/services/quotaSnapshotPoller.js:101-104`). The usage route's `isAuthExpiredMessage` looks for "expired", "401", and similar words (`usage/[connectionId]/route.js:19-24`), so the message must avoid them unless the problem really is auth.
- **Team or Business accounts.** `spendLimitUsage` may use `pooledLimit`/`pooledRemaining` rather than the `individual*` fields.
- **Percent above 100 or missing.** Clamp. If a percent field is missing, omit the row. Never report 0% used by default.
- **`billingCycleEnd` out of range.** `parseResetMs` drops resets more than 400 days out and treats them as 0 (`open-sse/services/quotaSnapshot.js:196-223`). The window then falls back to the 1h `snapshotTtlMs` TTL.
- **Model catalog cache after refresh.** `cursorModels` keys its catalog cache on `machineId + accessToken` (`open-sse/services/cursorModels.js:34-40`). After a refresh the cache simply misses. That is harmless, but old entries accumulate until their TTL expires.

## Workflows

### Primary: browser login (PKCE deep control)

1. The user opens the Cursor provider page and clicks Add. The `CursorAuthModal` (`src/shared/components/CursorAuthModal.js`) currently starts auto-import immediately on open (`:47-50`). It needs a method chooser, following the `KiroOAuthWrapper` precedent (`src/shared/components/KiroOAuthWrapper.js`): "Login with browser" (default) or "Import from Cursor IDE".
2. `GET /api/oauth/cursor/device-code`. The route requires `flowType === "device_code"` (`src/app/api/oauth/[provider]/[action]/route.js:272-279`). Add `cursor` to `noPkceDeviceProviders` (`:295-306`) because, like qoder, the provider generates its own PKCE pair.
   - The provider's `requestDeviceCode` generates a `verifier` (32 random bytes, base64url), `challenge = base64url(sha256(verifier))`, `uuid = randomUUID()`, and a new `machineId`.
   - It returns `{ device_code: uuid, verification_uri_complete: https://cursor.com/loginDeepControl?challenge&uuid&mode=login&redirectTarget=cli, expires_in, interval, codeVerifier, _cursorMachineId }`.
   - Precedent: `src/lib/oauth/providers/qoder.js:9-29`.
3. The modal opens the URL in a new tab and polls. `OAuthModal`'s `deviceCodeProviders` list (`src/shared/components/OAuthModal.js:286-297`) and its `extraData` builder (`:322-340`) need `cursor` entries. Each call is `POST /api/oauth/cursor/poll` with `{ deviceCode, codeVerifier, extraData }`. The deadline is `expires_in` (`:129-138`); use about 300s or more, since the default is 120s.
4. Each server poll makes one `GET https://api2.cursor.sh/auth/poll?uuid=…&verifier=…`:
   - 404 means pending: return `{ ok:false, data:{ error:"authorization_pending" } }`.
   - 200 returns `{ accessToken, refreshToken, authId? }`.
   - Any other status is an error. The route needs `cursor` in the poll dispatch (`route.js:550-582`); follow the qoder branch, which passes both `codeVerifier` and `extraData`.
5. On success, `mapTokens` decodes the JWT and returns `{ accessToken, refreshToken, expiresIn: exp - now, email: sub, displayName?, providerSpecificData: { machineId, userId: sub, authMethod: "browser" } }`. The route calls `createProviderConnection` (`route.js:584-603`). The dedup either upserts the matching row or creates a new one.
6. The modal shows success, and the page refreshes the connection list.

### Primary: refresh

- **Background:** every 5 min, `selectConnectionsNeedingRefresh` picks OAuth rows that have an RT and expire within `max(provider lead, 30 min)` (`backgroundTokenRefresh.js:44-71`). It then calls `checkAndRefreshToken(force)` (`src/sse/services/tokenRefresh.js:225-270`), which runs `refreshProviderCredentials` (a lock, then `REFRESH_HANDLERS[provider]`, then a merge). A `cursor` entry is needed in `REFRESH_HANDLERS` (`open-sse/services/tokenRefresh.js:142-181`), and optionally `oauth.refreshLeadMs` in the registry.
- **On request:** `chat.js:337` runs `checkAndRefreshToken` before each attempt.
- **On 401/403:** `chatCore.js:579-640` retries refresh up to 3 times, then re-executes. This path is gated by `executor.supportsRefresh !== false`. The Cursor executor sets `supportsRefresh = false` and `refreshCredentials()` returns `null` (`open-sse/executors/cursor.js:277-281`, `:830-832`). Both must change: delegate to `refreshProviderCredentials`, like the default executor.
- **Usage route or poller:** `refreshAndUpdateCredentials` (`src/app/api/usage/[connectionId]/route.js:31-127`) uses `executor.needsRefresh` and `refreshCredentials`, then persists.

### Primary: usage display and quota feed

1. Provider Limits calls `GET /api/usage/:id`, with eligibility coming from `features.usage` in the registry (`src/shared/constants/providers.js:224`). Add `features.usage: true` to `open-sse/providers/registry/cursor.js:58-60`.
2. `getUsageForProvider` looks up `USAGE_HANDLERS.cursor` (`open-sse/services/usage.js:42-76`). It POSTs `aiserver.v1.DashboardService/GetCurrentPeriodUsage` and `/GetPlanInfo` with Connect JSON (`Content-Type: application/json`, `Connect-Protocol-Version: 1`, Bearer, body `{}`). A live probe confirmed Bearer alone works.
3. The handler returns `{ plan, quotas: { "Total": {used,total:100,remainingPercentage,resetAt}, "Auto + Composer": …, "API": …, "On-demand": {used$, total$, …} } }`, following the percent-row style of `makeQuota` in kimi (`open-sse/services/usage/kimi.js:92-111`).
4. `recordUsageSnapshot` stores the windows and the plan tier (`quotaSnapshotSync.js:175-224`). The route attaches `quotaSnapshot.effectiveWeight`.
5. UI: `parseQuotaData`'s default branch drops `remainingPercentage` (`src/app/(dashboard)/dashboard/usage/components/ProviderLimits/utils.js:675-686`), so add a `cursor` case, as kimi and ollama have. The dollar row should use a display that is not a percentage; `isCreditBalance` and `currency` exist for deepseek (`:609-626`).
6. When cursor is weighted, the background poller (`quotaSnapshotPoller.js:87-123`) repeats steps 2 to 4 each minute for stale snapshots (older than 15 min).

### Error recovery

| Situation                                    | Behavior (target)                                                                                                                                                                                                                                                                                                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| User closes modal mid-poll                   | `pollingAbortRef` stops the loop (`OAuthModal.js:141-155`, `:509-516`). Nothing is persisted. The upstream `uuid` expires on its own.                                                                                                                                                                                                |
| Poll deadline reached                        | "Authorization timeout" error step. The user retries, which generates a new uuid, verifier, and machineId.                                                                                                                                                                                                                           |
| Poll returns non-404 error, or network error | Map fatal statuses to `expired_token` or `access_denied` so the modal stops (`OAuthModal.js:173-175`). Other errors keep polling until the deadline. pi-cursor aborts after 3 consecutive errors.                                                                                                                                    |
| Transient refresh failure                    | Keep the current token (still valid for weeks). Background retries on the next tick.                                                                                                                                                                                                                                                 |
| Permanent refresh failure (RT revoked)       | Return `unrecoverable_refresh_error`. The chat 401 path then locks the account via `markAccountUnavailable` (`auth.js:320-383`, `testStatus: "unavailable"`, `lastError`). Routing falls back to the next account. The user re-logs in, and dedup plus `resetHealthStateOnActivation` (`connectionsRepo.js:31-49`) clears the locks. |
| Chat `unauthenticated` (401)                 | Requires the classifier fix. Refresh, retry once, then fall back to another account.                                                                                                                                                                                                                                                 |
| Chat `resource_exhausted` (429)              | Backoff lock, then the next account. Weighted mode also excludes the account through the snapshot until `billingCycleEnd`.                                                                                                                                                                                                           |
| Usage 401                                    | The handler returns a message containing "expired" or "re-authorize". The usage route force-refreshes once when an RT exists (`route.js:186-194`).                                                                                                                                                                                   |
| Imported token past real `exp`, no RT        | Chat returns 401, the account locks for `COOLDOWN.long`, and the user must re-import or switch to browser login.                                                                                                                                                                                                                     |

## Domain Model

### Entities

- **ProviderConnection** (`providerConnections` table; `src/lib/db/repos/connectionsRepo.js`). Cursor-relevant fields: `provider:"cursor"`, `authType:"oauth"`, `accessToken`, `refreshToken` (null when imported), `expiresAt` (from JWT `exp`), `email` (= JWT `sub`, the dedup key), `displayName?`, `testStatus`, `lastError`, `errorCode`, `backoffLevel`, `modelLock_<model>`, `lastRefreshAt`, `priority`, `lastUsedAt`, `consecutiveUseCount`. `providerSpecificData` holds `machineId` (stable), `userId` (= sub), `authMethod` (`"imported"` or `"browser"`), `ghostMode?`, `planTier?`, `planTierManual?`, `planTierCheckedAt?`, `weight?`, and proxy fields.
- **PKCE login attempt** (transient, client-held like qoder): `{ uuid, verifier, challenge, machineId, loginUrl, expiresAt }`. Nothing is stored on the server.
- **Quota snapshot** (in memory, per connection; `open-sse/services/quotaSnapshot.js`): `{ provider:"cursor", planTier, windows:[{kind, usedFraction, resetsAt=billingCycleEnd, source:"probe"}], updatedAt }`.
- **Usage payload** (not persisted): `{ plan, quotas{name→{used,total,remainingPercentage,resetAt,isCreditBalance?}} }`, or `{ message }`.

### State transitions (connection auth lifecycle)

```text
            import (no RT)                         browser login (RT)
 [none] ───────────────────► IMPORTED ◄──re-import──  BROWSER ◄──── [none]
                               │   └──browser re-login (same sub)──► BROWSER
                               │                                     │  ▲
                   exp passes / 401                     refresh ok   │  │ (rotates AT/RT,
                               ▼                                     ▼  │  expiresAt=exp)
                         UNAVAILABLE ◄──401 + refresh permanent fail─ REFRESHING
                    (modelLock, testStatus=unavailable,                  │
                     lastError; routing skips)                transient fail → stays BROWSER
                               │
                  re-login / re-import (same sub) → resetHealthStateOnActivation → ACTIVE
```

Quota axis (independent of auth): `HEADROOM_OK` → (Total ≥ 95%, weight 0) `EXHAUSTED_BY_SNAPSHOT` → (`billingCycleEnd` passes, window expires) `HEADROOM_OK`. `resource_exhausted` adds a short backoff `modelLock` (at most 30 min) on top.

## Success Criteria

1. From a remote or Docker instance, "Login with browser" creates an active Cursor connection with `refreshToken` set, a generated `machineId`, `expiresAt` equal to the JWT `exp` (about 60 days), and `authMethod` set to the browser method. Chat through `cu/<model>` works.
2. A browser re-login to the same account (same `sub`) as an existing imported or browser row updates that row in place. The row count is unchanged. `id`, `priority`, `machineId`, `weight`, and a manual `planTier` are preserved, and model locks and errors are cleared.
3. A different Cursor account creates a second row.
4. Import still works. It stores the JWT-based `expiresAt` and never nulls an existing refresh token.
5. With `expiresAt` forced near now, the background refresh rotates the token and persists a new `accessToken`/`expiresAt`, while `machineId` stays unchanged. A chat 401 triggers refresh and one retry.
6. A revoked refresh token yields `unrecoverable_refresh_error`. The connection ends up `unavailable` with a meaningful `lastError`, and routing falls back to another Cursor account.
7. A Connect `unauthenticated` error from the chat path surfaces as 401, not 400.
8. Provider Limits shows the plan name and the Total, Auto + Composer, API, and On-demand rows with reset at `billingCycleEnd`. Values match cursor.com/dashboard.
9. With `weighted` configured, `quotaSnapshot.planTier` is `"ultra"` (or the matching tier), `effectiveWeight.base` comes from `PLAN_CAPACITY.cursor`, and an account at 100% Total has weight 0.
10. Lint passes, and the unit tests stay green against `known-fails.txt`. The alias, OAuth, and provider baselines are regenerated only when the registry changed intentionally.

## Open Questions

1. **Auto + Composer and API windows in routing.** How should these map to snapshot kinds? The `"model:<id>"` matcher is token-based (`quotaSnapshot.js:255-264`). "Auto" applies to the `default` model id and `composer-*`. "API" applies to every named model. Options: map Auto to `model:default` plus `model:composer`, map API to nothing and rely on Total, or add a Cursor-specific global kind. Recording only Total may be the simplest correct first cut.
2. **Refresh endpoint.** The feature description and pi-cursor use `auth/exchange_user_api_key` with Bearer RT. openchamber uses the Auth0 `POST api2.cursor.sh/oauth/token` (`grant_type=refresh_token`, `client_id KbZUR41cY7W6zRSdpSUJ7I7mLYBKOCmB`), and a `shouldLogout: true` body means permanent failure. Which one is authoritative for PKCE-issued tokens? Does it rotate the RT, and what does it return for a revoked RT? Verify live in `9router-dev`.
3. **Imported rows gaining a refresh token.** Should auto-import also read `cursorAuth/refreshToken` from `state.vscdb` so imported rows become refreshable? Note that doing so shares a rotating RT with the running IDE, which could cause refresh races or logouts of the IDE session.
4. **Where the verifier lives.** Should the PKCE verifier stay client-side, like qoder's pattern of returning `codeVerifier` to the browser, or go into a server-side session keyed by `uuid`, like the codex/xai session registry? The dashboard is authenticated, so client-side is consistent with precedent.
5. **Display identity.** Should we fetch a real email for `displayName` (for example via `GetMe` or a stripe profile endpoint) while keeping `email = sub` as the dedup key? Or should dedup move to `providerSpecificData.userId`? That needs a Cursor case in `createProviderConnection` plus migration of existing rows.
6. **Plan capacity values.** Confirm the exact `planName` strings ("Pro+", "Ultra", "Business", "Team", "Free Trial"?) and their ratios before hard-coding them. Mark uncertain rows `_verify`, as the other tables do.
7. **Exhaustion cooldown.** When `resource_exhausted` arrives and the snapshot says Total is at 100%, should Cursor pass `resetsAtMs = billingCycleEnd`? Given the 30-min cap, the account would still be re-probed about every 30 min. Is that acceptable, or should Cursor be exempt from the cap as Antigravity is?
8. **Backfilling imported rows.** Should a one-shot backfill correct `expiresAt` from the JWT `exp` on existing imported rows, or should they be left alone until the next re-import?
