# Security Research: yan-385-cursor-pkce-usage

## Executive Summary

The feature adds a server-side Cursor "deep-control" PKCE login (`cursor.com/loginDeepControl` +
`api2.cursor.sh/auth/poll`), stores the resulting access and refresh tokens plus a generated
`machineId` in the connection row, refreshes tokens, and fetches plan and usage data from
`api2.cursor.sh` DashboardService. All upstream hosts are fixed. The only new cryptography is PKCE
(`crypto.randomBytes` + SHA-256), which `src/lib/oauth/utils/pkce.js` already covers. **No new
dependencies are needed.**

The design is sound if the PKCE verifier stays on the server. The main risks come from copying
existing patterns that are weaker than this flow needs:

1. The generic device-code route sends `codeVerifier` to the browser and accepts it back from the
   request body (`src/app/api/oauth/[provider]/[action]/route.js:315-320`, `:544`). Cursor must not
   copy this. The verifier and uuid belong in a server-side session map keyed by an opaque id.
2. The provider list/detail APIs strip the top-level token fields but return
   `providerSpecificData` unchanged (`src/app/api/providers/route.js:84-92`,
   `src/app/api/providers/[id]/route.js:131-135`). If the refresh token or access token is put in
   `providerSpecificData`, it reaches the browser.
3. Once Cursor connections have a `refreshToken`, three paths can refresh them: the background
   refresher (`src/sse/services/backgroundTokenRefresh.js:44-71`), the request path, and the usage
   route (`src/app/api/usage/[connectionId]/route.js:31-127`). Their only concurrency guard is the
   in-process `dedupRefresh` (`open-sse/services/tokenRefresh/dedup.js:1-31`).
4. Tokens are stored as plaintext JSON in SQLite, the same as every other provider
   (`src/lib/db/repos/connectionsRepo.js:5-27,79`). Cloud sync is not present in this tree, so no
   off-box upload path exists.

No CRITICAL vulnerability exists in the codebase today. Two items are rated CRITICAL because they
are must-do design requirements: if they are missed, the feature directly exposes credentials.

## Authentication and Authorization

- **Route protection.** Any new route under `/api/oauth/cursor/*` (for example `pkce/start` and `pkce/poll`, or `[action]` branches) falls under `PROTECTED_API_PATHS` `"/api/oauth"` (`dashboardGuard.js:44`) and the deny-by-default `/api/*` gate (`dashboardGuard.js:203-209`). Access requires a valid `auth_token` JWT (`JWT_SECRET`-signed, `dashboardSession.js:12-24`), a CLI token, or `requireLogin=false`. The usage route `/api/usage/*` is also protected (`dashboardGuard.js:43`).
- **CSRF.** The session cookie is `SameSite=lax`, so the start and poll endpoints must be **POST**, never GET: a lax cookie still goes out on top-level GET navigations. Route handlers call `request.json()` without checking `Content-Type`, so require `Content-Type: application/json` on start. That forces a CORS preflight on cross-origin callers.
- **Session binding.** In a single-user dashboard, binding `sessionId` to a specific dashboard session is optional. An opaque, unguessable `sessionId` (122-bit UUIDv4) that is single-use with a TTL is enough. For the future users/teams work (P-YAN-8), store the creating user id in the session and check it on poll.
- **IP handling.** No change to `custom-server.js` is needed. The feature relies on no client IP decisions. If rate limits are added (W4/W5), key them per `sessionId` or globally, not per `x-forwarded-for`. The existing trusted-peer model (`dashboardGuard.js:92-118`) already handles loopback detection.

## Input Validation

- **Start:** takes no client input except an optional label. Ignore any client-sent `uuid`, `verifier`, `challenge`, or `machineId`.
- **Poll:** `sessionId` must be a string matching a UUID regex and present in the map. Otherwise return 404 `{status:"unknown"}` (mirrors `route.js:222`).
- **Upstream poll response:** accept success only when `accessToken` and `refreshToken` are non-empty strings of bounded length (for example ≤ 8 KB each). Treat 404 as pending (the endpoint returns 404 until the user approves, per [pi-cursor docs](https://www.npmjs.com/package/@schultzp2020/pi-cursor)). Treat anything else as an error with a fixed message.
- **Refresh and usage responses:** parse with `try/catch` around `res.json()`. Cap body size by checking `content-length` or reading at most N bytes before parsing (about 256 KB is ample). Coerce numeric fields with `Number.isFinite` checks before they reach the UI. Render plan names and strings as text (React escapes by default; do not use `dangerouslySetInnerHTML`).
- **SSRF:** all URLs must be constants in `CURSOR_CONFIG` / `open-sse/config` (`https://cursor.com/loginDeepControl`, `https://api2.cursor.sh/auth/poll`, `https://api2.cursor.sh/auth/exchange_user_api_key`, `https://api2.cursor.sh/aiserver.v1.DashboardService/...`). Never derive a host from request params. Unlike the `authorize` branch, which forwards arbitrary query params into `meta` (`route.js:130-151`), Cursor needs none. Build the login URL with `URLSearchParams`, not string concatenation.

## Infrastructure Security

- **Timeouts:** about 10 s per upstream call via `fetchWithTimeout`. The session TTL (about 10 min) bounds total polling.
- **Proxy pools:** `proxyAwareFetch` may route Cursor calls through per-connection or user-configured proxies (`src/lib/network/connectionProxy.js`). This is the same trust level as the chat path, so tokens transit those proxies. Accept this.
- **Process model:** the session map is per-process. Bare `next dev` and multi-worker setups can split start and poll across processes, making a session appear "unknown". Document this. The codex/xai flows already live with it. Prod uses a single `custom-server.js` process.
- **Container/prod:** prod runs in Docker (`9router` container). Session loss on restart only means the user must restart login.

## Secure Coding Guidelines

1. Generate `{sessionId, uuid, verifier, challenge, machineId}` server-side. Return `{sessionId, loginUrl, expiresAt}` only.
2. Keep sessions in a dedicated module (for example `src/lib/oauth/cursorPkceSessions.js`) with `create/get/consume/sweep`. Its getter returns a redacted view (no verifier). Enforce a size cap and TTL. Delete on done/error.
3. The poll handler does one upstream call per request, rate-limited per session. On success it calls `createProviderConnection({provider:"cursor", authType:"oauth", accessToken, refreshToken, expiresAt, email, providerSpecificData:{machineId, authMethod:"pkce", userId}})` and returns `{status:"done", connection:{id, provider, email}}`.
4. Put token fields only at the top level of the connection. Put nothing secret in `providerSpecificData`.
5. Add a `cursor` entry to `REFRESH_HANDLERS` (`open-sse/services/tokenRefresh.js:142-181`) implemented through `dedupRefresh`. Classify only explicit 401/403 as `invalid_grant`. Keep the existing refresh token when the response lacks a new one. Flip `CursorExecutor.supportsRefresh` and implement `refreshCredentials` only for connections that have a refresh token.
6. Error messages come from fixed strings plus HTTP status. No response bodies, URLs, or headers. Log `{provider:"cursor", status, sessionId|connectionId}` only.
7. Usage fetcher (`open-sse/services/usage/cursor.js`, registered in `USAGE_HANDLERS`, `open-sse/services/usage.js:42-76`): Bearer access token, fixed URLs, `fetchWithTimeout`, return `{message}` on auth failure so `isAuthExpiredMessage` (`usage/[connectionId]/route.js:19-24`) triggers a refresh.
8. Tests (vitest, isolated DATA_DIR):
   - the start response has no `verifier`;
   - poll with an unknown or expired `sessionId` returns unknown;
   - poll ignores body-supplied `uuid`/`verifier`;
   - a success response contains no token fields;
   - `/api/providers` output for a Cursor PKCE connection contains no token strings;
   - the refresh classifier maps 404 to retryable and 401 to `invalid_grant`;
   - concurrent refreshes dedupe into one upstream call.

## Trade-off Recommendations

| Decision                       | Recommendation                                                                                              | Rationale                                                                                                                                 |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Verifier location              | **Server memory** (not client, not DB)                                                                      | Removes the C1 exposure. Losing it on restart costs one retry. Persisting it to the DB adds at-rest exposure for no benefit.              |
| Who drives polling             | **Dashboard-driven poll → one upstream call per request, rate-limited**                                     | No background timers to leak. Stops naturally when the user closes the modal. Matches the existing `poll-status` UX (`route.js:205-243`). |
| Token encryption               | **Stay plaintext, consistent with the other providers**                                                     | A Cursor-only scheme adds complexity without protecting the other 40 providers. File a cross-cutting issue instead.                       |
| Refresh endpoint               | **Implement the spec's `exchange_user_api_key`, gated behind live verification; keep a retryable fallback** | Sources conflict (W3). Wrong classification is the real risk, not the endpoint choice.                                                    |
| Protection level of new routes | **Default `/api/oauth` protection; optionally `ALWAYS_PROTECTED` for start**                                | This matches the other OAuth flows. `ALWAYS_PROTECTED` hardens `requireLogin=false` deployments at small UX cost.                         |
| Usage polling frequency        | **Reuse the existing quota snapshot cache; no auto-poll faster than existing providers**                    | Reduces ToS and abuse signal (A5).                                                                                                        |

## Open Questions

1. **Refresh contract:** does `POST api2.cursor.sh/auth/exchange_user_api_key` with `Authorization: Bearer <refreshToken>` return a fresh `accessToken` for PKCE-issued refresh tokens? Or is `POST /oauth/token` (`grant_type=refresh_token`, `client_id`) required? Does either rotate the refresh token? Verify on the `9router-dev` container.
2. **Poll method:** GET with query params (spec) or POST with JSON `{uuid, verifier}` (as some clients do)? POST keeps the verifier out of URL logs.
3. **Access-token lifetime:** is the JWT `exp` about 1 h (as `exchange_user_api_key` tokens reportedly are) or longer? This sets the refresh lead time (`REFRESH_LEAD_MS`).
4. **machineId acceptance:** does Cursor accept a random 64-hex `machineId` for PKCE-issued tokens without extra registration? This is functional, but a rejection could push implementers toward reading the host IDE's real id, which has privacy implications.
5. **Multi-user future (P-YAN-8):** should PKCE sessions be bound to the creating dashboard user id now, to avoid a retrofit?
6. **Should `/api/oauth/cursor/*` start and poll join `ALWAYS_PROTECTED`** given W8? This is a product decision for `requireLogin=false` users.
