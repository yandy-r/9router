# Practices Research: yan-385-cursor-pkce-usage

## Executive Summary

Nearly everything this feature needs is already in the repo. The one thing that is actually new is Cursor's HTTP contract (the login URL, poll, exchange, and Dashboard RPC calls). Cursor's deep-control login works the same way as the existing **Qoder** flow: build a local PKCE pair and a nonce/uuid, open a browser URL, then poll until the upstream returns a token (404 means pending). Because of that, Cursor can be a normal `flowType: "device_code"` provider module. It can go through the generic PKCE branch of `src/app/api/oauth/[provider]/[action]/route.js` without any route edits, because `device_code` carries the uuid and `codeVerifier` is threaded through for free. Refresh plugs into `REFRESH_HANDLERS` and `canRefreshCredentials`. Usage plugs into `USAGE_HANDLERS`, `features.usage`, and the three `cursor` cases in quota-snapshot (`PLAN_CAPACITY`, `kindForName`, `planTierFor`). The main risks are these: (a) JWT decoding is already copy-pasted about 6 times, so do not add a 7th; (b) `CursorExecutor.buildHeaders` throws when `machineId` is missing, and a PKCE login has no IDE machineId; (c) `tokenRefresh/providers.js` (869 lines) and `executors/cursor.js` (835 lines) are already over the ~500-line cap.

## Modularity Design

Minimal boundaries: 1 new provider-side service method set, 1 new open-sse usage file, 1 new small refresher file, plus one-line wiring edits.

1. **`src/lib/oauth/services/cursor.js` (`CursorService`)** owns all Cursor _auth_ HTTP, following the `QoderService` layout: `initiateDeepControlLogin(codeChallenge)` → `{uuid, verificationUriComplete}`, `pollDeepControl({uuid, codeVerifier})` → `{status:"pending"} | {status:"ok", accessToken, refreshToken}`, and `exchangeRefreshToken(refreshToken)`. Delete the dead `generateChecksum`/`buildHeaders`/`detectOS`/`detectArch` (`:27-86`), which have no callers and an outdated checksum algorithm. That keeps the file under the cap. Make `extractUserInfo` call `decodeJwtPayload`, and add an exp → ISO helper next to it (or a tiny `jwtExpiresAt(token)` in `providerHelpers.js` so every caller shares it).
2. **`src/lib/oauth/providers/cursor.js`**: `flowType: "device_code"`, `requestDeviceCode(config, codeChallenge)` returns `{device_code: uuid, user_code, verification_uri_complete, expires_in, interval}`, `pollToken(config, deviceCode, codeVerifier)`, and `mapTokens` (email/userId via `extractUserInfo`, `expiresIn` from JWT exp, `providerSpecificData:{machineId: crypto.randomUUID(), authMethod:"pkce"}`). `import_token` has no other consumers besides the display string at `import/route.js:74`, so flipping the flowType is safe.
3. **`open-sse/services/tokenRefresh/cursor.js`** (new, about 30 lines) holds `refreshCursorToken`: `dedupRefresh`, a lazy import of `CursorService` (xai precedent), and the invalid_grant mapping. Import it in `tokenRefresh.js` and add it to `REFRESH_HANDLERS`. Do not add to `tokenRefresh/providers.js`, which is 869 lines.
4. **`open-sse/services/usage/cursor.js`** (new): `getCursorUsage(accessToken, proxyOptions)` calls GetCurrentPeriodUsage and GetPlanInfo in parallel (`Promise.allSettled`) via `fetchWithTimeout`, then passes both results to a pure, exported `parseCursorUsage(periodJson, planJson)` → `{plan, quotas, message}`.
5. **Wiring edits (one line or a few lines each):** `usage.js` handler, registry `features.usage` / `transport.usage` / oauth URLs, `executors/cursor.js` (`canRefreshCredentials`, `refreshCredentials`, `needsRefresh`, drop `supportsRefresh=false`), `quotaSnapshot.js` `PLAN_CAPACITY.cursor`, `quotaSnapshotSync.js` two `case "cursor"`, the ProviderLimits `case "cursor":` label, the OAuthModal list, and a CursorAuthModal button. Optionally, `testUtils.js:87` → `{ checkExpiry: true, refreshable: true }`.

## Abstraction vs. Repetition

- **Abstract (reuse):** PKCE (`utils/pkce.js`), JWT decode (`decodeJwtPayload`), response reading (`readTokenResponse`), refresh dedup (`dedupRefresh`), usage fetch/reset parsing (`usage/shared.js`), and the quota row shape (copy the _shape_, not `makeZedQuotaRow`; about 10 lines of clamping is acceptable).
- **Accept repetition:** a 1-line `case` in each of `kindForName` / `planTierFor` / `parseQuotaData`, and one entry each in the OAuthModal device list and `REFRESH_HANDLERS`. These are the established per-provider extension points, so do not generalize them in this PR.
- **Do not duplicate:** Cursor endpoint strings. They belong only in `registry/cursor.js` (`oauth` for auth URLs, `transport.usage` for Dashboard paths). `CursorService` reads them via `CURSOR_CONFIG`, and the usage fetcher reads them via `U("cursor")`.
- **Known debt to leave alone:** the three hand-maintained device-provider lists (`route.js:294`, `:551`, `OAuthModal.js:286`). Cursor only goes in the OAuthModal one.

## Interface Design

- `requestDeviceCode(config, codeChallenge)` → `{ device_code: uuid, user_code: uuid.slice(0,8).toUpperCase(), verification_uri: config.loginUrl, verification_uri_complete:`${loginUrl}?challenge=…&uuid=…&mode=login`, expires_in: 300, interval: 2 }`.
- `pollToken(config, uuid, codeVerifier)` → pending: `{ ok:false, data:{ error:"authorization_pending" } }`; done: `{ ok:true, data:{ access_token, refresh_token, expires_in } }`; missing verifier or uuid → `{ ok:false, data:{ error:"invalid_request" } }`.
- `mapTokens(data)` → `{ accessToken, refreshToken, expiresIn, email, providerSpecificData:{ machineId, authMethod:"pkce", userId } }`. **`machineId` is required**: `CursorExecutor.buildHeaders` throws without it (`executors/cursor.js:288`), and `cursorModels.js` keys its cache on it.
- `refreshCursorToken(refreshToken, log)` → `{ accessToken, refreshToken (rotated or same), expiresAt: ISO from JWT exp }` | `{ error:"invalid_grant" }` | `null`.
- `getCursorUsage(accessToken, proxyOptions)` → `{ plan: "pro"|"pro_plus"|"ultra"|…, quotas: { "Monthly": {used,total,remainingPercentage,resetAt} , …}, message }`. On 401/403 → `{ message }` (zed pattern `usage/zed.js:211-219`). Never throw.
- `plan` should be a lowercase tier id that matches the `PLAN_CAPACITY.cursor` keys. Pass it through `sanitizePlanTier`, and keep a human label separate only if the UI needs one.

## Testability Patterns

- **fetch mocking:** usage fetchers mock `open-sse/utils/proxyFetch.js` via `vi.mock` (`tests/unit/deepseek-usage.test.js:3-7`, `jsonResponse` helper). Auth services that use global `fetch` swap `global.fetch` (`tests/unit/cursor-models.test.js:8`).
- **Pure parsers:** export `parseCursorUsage` and assert on fixtures, with no network (zed and kimi usage tests).
- **Isolation:** `tests/setup` gives each file its own temp `DATA_DIR`, so no DB setup is needed.
- **CRITICAL tests only (3 files, merge if possible):**
  1. `tests/unit/cursor-pkce-login.test.js`: `requestDeviceCode` URL contains `challenge = S256(verifier)` and uuid; `pollToken` 404 → pending, 200 → `access_token`; `mapTokens` sets `machineId` and derives `expiresIn` from JWT `exp`.
  2. `tests/unit/cursor-token-refresh.test.js`: exchange success → new token plus `expiresAt` from JWT; 401 → `{error:"invalid_grant"}`; `CursorExecutor.canRefreshCredentials({})` is false (keeps the no-futile-refresh guarantee for imported tokens).
  3. `tests/unit/cursor-usage.test.js`: `parseCursorUsage` fixture → quotas and plan tier; `getUsageForProvider({provider:"cursor"})` dispatches (one case); `kindForName("cursor", …)==="month"`.
- **Skip:** UI/modal tests, route tests (the generic path is already covered), and baseline regeneration (only `usage` / `features` / new non-injected oauth keys change, and those are excluded or not snapshotted). Run `tests/__baseline__/verify-providers.mjs` and `verify-oauth-urls.mjs` once to confirm.

## Open Questions

1. **Refresh semantics:** is `POST api2.cursor.sh/auth/exchange_user_api_key` called with the poll's `refreshToken` as bearer (pi-cursor treats the durable credential as an "apiKey"), or does IDE-style `/oauth/token` with `grant_type=refresh_token` apply? Confirm the request and response shape, and whether the RT rotates, before coding `refreshCursorToken`.
2. **Poll response contract:** confirm the pending status codes (404 vs 202), the success fields (`accessToken`, `refreshToken`, `authId`?), and the `loginDeepControl` params (`challenge`, `uuid`, `mode=login`).
3. **Identity/dedup:** Cursor JWT `sub` is usually `auth0|user_…`, with no `email`. Should PKCE rows reuse `extractUserInfo` (`email = sub`) to match imported rows, or fetch a real email (Dashboard `GetMe`?) and risk duplicates against existing imports?
4. **Dashboard auth:** does GetCurrentPeriodUsage/GetPlanInfo accept a plain `Authorization: Bearer` with Connect-JSON, or does it need `x-cursor-checksum` / client headers from `buildCursorHeaders`?
5. **Plan tier ids and weights:** what are the exact `planName` values from GetPlanInfo (`free`/`hobby`, `pro`, `pro_plus`?, `ultra`, `business`/`team`)? Proposed `PLAN_CAPACITY.cursor`: `free 0.05, pro 1, pro_plus 3, ultra 20, business 1`, marked `// _verify` as the other entries are.
6. **Imported-token refresh:** should auto-import also read `cursorAuth/refreshToken` (`auto-import/route.js:10`) so existing imported connections become refreshable? Also, should the import route stop stamping the fake 24h expiry and use JWT `exp` instead?
7. **Quota rows:** show a single "Monthly" (total % used) row, or split Auto vs API buckets? A single row is the KISS default, and the snapshot collapses to `month` either way.
